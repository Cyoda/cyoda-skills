# Help map for cyoda-go v0.8.4

Which `cyoda help` sections the dev skills may defer to, and which are untrustworthy.

**How to use it (skill tasks 7-12):** point a skill at a row only if its verdict is `ok`, or `wrong -> #N` / `missing -> #N` with `#N` in the spec's Upstream table. Rows marked `TO FILE` are confirmed mismatches not yet filed; the skill must not rely on those sections until the issue is listed in the Upstream table.

**Method.** Each section was read with `cyoda help <path> --format=json | jq -r '.sections[] | select(.name=="<SECTION>") | .body'` (binary v0.8.4) and checked against the cyoda-go source at tag v0.8.4. Depth: the important claims were verified (endpoints and routes, methods, field and parameter names, enum values, defaults and limits, ordering and precedence rules, error codes and HTTP statuses). Descriptive prose, examples' sample values and storage-backend internals were not checked line by line. For `auth tokens` / `auth clients` / `config auth` / `config grpc` the help actions are text topics (`cyoda help auth tokens`), and the JSON form works the same.

Source references use `SRC` = cyoda-go at v0.8.4.

## To file

Each is a confirmed mismatch not yet filed. Proposed milestone v0.9.0 (as for the earlier quick help fixes). Numbers are local labels only; the issue numbers go in the Upstream table after filing.

**(1) `config` Profile loader names the wrong files.** Help (`cyoda help config`, "Profile loader"): "For each name `N`, a file `cyoda.N.env` is loaded from the working directory". Code (`app/envfiles.go:20-44`): loads `.env` then `.env.<profile>` in declaration order from the working directory, e.g. `CYODA_PROFILES=postgres,otel` loads `.env`, `.env.postgres`, `.env.otel`. `cyoda help run` ("RUN MODES") already says `.env.postgres`, so the two topics contradict each other. The v0.8.4 audit (setup row) repeated the `cyoda.N.env` form from the config help; fix the audit/skill when the help is corrected.

**(2) `audit` ENDPOINTS: StateMachine `eventType` list is incomplete.** Help lists 14 values ending `... PAUSE_FOR_PROCESSING, STATE_PROCESS_RESULT` as "one of". The generated enum (`api/generated.go:1117-1120`) also has `SCHEDULED_TRANSITION_ARM`, `SCHEDULED_TRANSITION_CANCEL`, `SCHEDULED_TRANSITION_EXPIRE`, `SCHEDULED_TRANSITION_FIRE`. `cyoda help workflows` ("SCHEDULED TRANSITIONS", Audit trail) describes these four events, so a skill following `audit` alone would filter them out or treat them as unknown.

**(3) `helm` VALUES: `gateway.parentRefs` empty list does not fail the chart.** Help: "When `true`, `gateway.parentRefs` MUST be set to a non-empty list ... an empty list causes install to fail." `helm template cyoda deploy/helm/cyoda --set postgres.existingSecret=a --set jwt.existingSecret=b --set cluster.hmacSecret.existingSecret=c --set monitoring.metricsBearer.existingSecret=d` renders HTTPRoute and GRPCRoute with `parentRefs: []` (`templates/gateway-httproute.yaml:12-13`, `gateway-grpcroute.yaml:9-10`; no `fail` and `values.schema.json:105` only says `"type": "array"`). Whether a real cluster rejects it depends on the Gateway API CRDs (not tested here), so the install either fails for a different reason (CRDs absent) or creates routes attached to nothing. The `run` "Minimal install" (see #682) also omits gateway/ingress, so it ends up with `gateway.enabled=true` and no parent. Suggest: enforce with `required` in the template, or document the real behaviour, and add `--set gateway.enabled=false` (or ingress settings) to the minimal install.

**(4) `helm` VALUES omits `migrate.postgres.existingSecret` and `existingSecretKey`.** The section opens "All top-level keys in `deploy/helm/cyoda/values.yaml`". `values.yaml` has `migrate.postgres.existingSecret` / `existingSecretKey` (default `""` / `dsn`), used by the pre-upgrade Job via `templates/_helpers.tpl:100-116` (falls back to `postgres.existingSecret` when empty). Help documents only `migrate.activeDeadlineSeconds`, `backoffLimit` and `resources`. Low severity; matters for deployments that use a separate migration credential.

**(5) `workflows` IMPORT REQUEST / EXPORT RESPONSE do not state the import is strictly decoded and the export is not re-importable.** Code: `internal/domain/workflow/handler.go:86-90,191-199` decodes the import body with `DisallowUnknownFields()` and rejects trailing data, so any extra field anywhere gives `400 BAD_REQUEST "invalid JSON: json: unknown field ..."`. The export (`handler.go:452`) is `{entityName, modelVersion, workflows}`; POSTing it back verbatim hits the unknown-field rule on `entityName`. The correct round trip is `jq '{importMode:"REPLACE", workflows}'`. Neither section says so; the only "round-trip" mentions concern `annotations` and `active`. Needed by `deploy` (re-seed) and `build`.

**(6) `workflows` ProcessorConfig: `responseTimeoutMs` "0 means use node default".** Help: "`responseTimeoutMs` ... `0` means use node default". Code: a non-positive value falls back to the server-side constant `defaultResponseTimeoutMs = 30000` (`internal/grpc/dispatch.go:33,122-124`), not anything the compute node declares. `cyoda help search` (FunctionCondition) documents the 30000 default correctly. Low severity, but the 30 s figure is what `compute` and `debug` need. Not counted as its own row; it is folded into the `workflows` PROCESSORS row.

## Notes for the skill tasks

- Do not hard-code values that help can supply: schema version (`workflows schema-version versions`), keepalive timings (`grpc` KEEPALIVE / `config grpc`), defaults (`quickstart` DEFAULTS).
- `workflows` PROCESSORS and `grpc` TAG ROUTING disagree about tags (#679); `compute` and `debug` cite `grpc` TAG ROUTING only.
- `docs` should tell users that `cyoda help errors` lists every code in SEE ALSO, not in the index body.
- Rows not covered here because they need no help section: `status` version probe (`GET /api/help` returns `{schema, version, topics}`, `internal/api/help.go:60-85`, taken from the audit, not re-verified in this pass).
