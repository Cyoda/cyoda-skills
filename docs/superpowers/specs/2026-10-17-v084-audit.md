## 0. Critical findings (fix first)

1. **The workflow `"version": "1"` is rejected.**
   - v0.8.1+ requires semver `MAJOR.MINOR` within the supported set; `"1"` gets `400 WORKFLOW_SCHEMA_VERSION_UNSUPPORTED`.
   - `cyoda help workflows schema-version versions` gives `{"current":"1.4","supported":[{"major":1,"minMinor":1,"maxMinor":4}]}`. See CHANGELOG 0.8.1 "Breaking" (version strictly validated).
   - Affected files: `build/templates/workflow.json:5` and `build/examples/hello-world.md:24`.
2. **You can't create entities against an unknown or UNLOCKED model.**
   - `POST /api/entity/JSON/{e}/{v}` returns `404 MODEL_NOT_FOUND` if the model was never imported, and `409 MODEL_NOT_LOCKED` if it is unlocked (`SRC/internal/domain/entity/service.go:206-217`; H:crud "Creating an entity requires the referenced model to be in LOCKED state"; H:models LIFECYCLE).
   - The skills' "discover mode: Cyoda infers the schema from the entities you post" model is therefore wrong.
   - The correct sequence:
     1. `POST /api/model/import/JSON/SAMPLE_DATA/{e}/{v}` with sample data (the model is UNLOCKED; imports merge additively).
     2. `PUT /api/model/{e}/{v}/lock`.
     3. Optionally `POST /api/model/{e}/{v}/changeLevel/{ARRAY_LENGTH|ARRAY_ELEMENTS|TYPE|STRUCTURAL}`, so that entity writes and processor output can extend the locked schema.
   - Affected: `build/SKILL.md:46`, `build/examples/hello-world.md:5-14,45`, `design/SKILL.md:37-41`, `debug/SKILL.md:50-53`, `test/templates/smoke-test.sh:20-23`.
3. **A PUT that triggers a transition with no body returns 400.**
   - `PUT /api/entity/JSON/{id}/{transition}` decodes the body as JSON, so an empty body gets `400 BAD_REQUEST "invalid JSON"` (`SRC/internal/domain/entity/handler.go:1072-1098` → `service.go:2117-2121`, `ingest/decode.go:21-31`).
   - A PUT also **replaces the payload wholesale**.
   - To fire a transition without changing data, use `PATCH /api/entity/JSON/{id}/{transition}` with `Content-Type: application/merge-patch+json`, `If-Match: *` (or a txId) and body `{}` (H:crud PATCH). Otherwise PUT the full current payload.
   - Affected: `build/examples/hello-world.md:42`, `test/templates/smoke-test.sh:34`.
4. **Workflow import is strict-decoded.**
   - Unknown fields anywhere in the import body get `400` (CHANGELOG 0.8.1 #264; `SRC/internal/domain/workflow/handler.go:87-91,191`).
   - The export response is shaped `{entityName, modelVersion, workflows}`, so it **cannot be re-POSTed verbatim** to `/workflow/import`. Convert it first with `jq '{importMode:"REPLACE", workflows}'`.
   - Affected: `migrate/SKILL.md:111-117`. Any deploy or re-seed flow will hit the same problem.
5. **Health probes use the wrong listener.**
   - `/readyz` and `/livez` are served only on the **admin** listener, `127.0.0.1:9091` (H:cli.serve LISTENERS; `SRC/internal/admin/admin.go:43-47`).
   - The API port exposes `GET /api/health`, which returns `{"status":"UP"}` (`SRC/internal/api/health.go:23`; mounted under the context path at `app/app.go:683,774-777`).
   - `${ENDPOINT}/readyz` against `:8080` therefore returns 404, and the skill reports "UNREACHABLE" for a healthy server.
   - Affected: `debug/SKILL.md:63`, `migrate/SKILL.md:29`, `setup/SKILL.md:70` (first probe). `cloud setup` is affected too (CLOUD).
6. **Compute-node tag routing is described backwards.**
   - The skill says "superset" and "case-insensitive". The code matches on **overlap**: at least one shared tag, exact case-sensitive string match after trimming (`SRC/internal/common/tags.go:7-20`, `internal/grpc/members.go:467-479`; H:grpc TAG ROUTING).
   - When several members match, one is picked at random. An empty `calculationNodesTags` matches any member of the tenant.
   - The help itself is inconsistent: H:workflows ProcessorConfig says "declares all required tags", but the code and H:grpc say overlap.
   - Affected: `compute/resources/grpc-patterns.md:58-62`, `debug/SKILL.md:42`.
7. **The timeouts are wrong.**
   - The default processor/criteria response timeout is **30 s** (`SRC/internal/grpc/dispatch.go:33 defaultResponseTimeoutMs = 30000`), overridable per processor with `config.responseTimeoutMs`.
   - Keep-alive: the server sends every `CYODA_KEEPALIVE_INTERVAL` = 10 s and evicts after `CYODA_KEEPALIVE_TIMEOUT` = **30 s** of inbound silence (H:grpc KEEPALIVE).
   - The skills say 60 s: `compute/SKILL.md:57`, `compute/examples/processor.md:38`, `compute/resources/grpc-patterns.md:39`, `debug/SKILL.md:43`.
8. **Two workflow features in the patterns file don't exist in that form.**
   - The "scheduled processor" (`design/resources/patterns.md:16`) is a fiction. Scheduled transitions are a `schedule` object on a transition (v0.8.3).
   - "Message-based transition fired by a CloudEvent" (`patterns.md:41`) does not exist. Edge messages never touch the workflow engine (H:messages DESCRIPTION).
9. **The Homebrew tap is outdated.** It is now `brew install cyoda/cyoda-go/cyoda` (`SRC/README.md:30,43`; `MAINTAINING.md:13`; the installed tap is `cyoda/cyoda-go`). The skill uses `brew tap cyoda-platform/cyoda-go`, at `setup/SKILL.md:29,44`.
10. **The docs site repeats bugs 1-3.**
    - `cyoda-docs/src/content/docs/getting-started/install-and-first-entity.mdx` uses `"version": "1"` (L107), creates an entity with no model import or lock (L146, "Cyoda discovers the schema from the sample you send"), and PUTs a transition with no body (L171).
    - The skills appear to have been derived from that page. `cyoda:docs` falling back to the web will re-introduce the bugs until the docs are fixed.

### Storage backends

`CYODA_STORAGE_BACKEND` selects the backend:
- **memory:** the bare default; not persisted.
- **sqlite:** after `cyoda init`, or in compose. Single process.
- **postgres:** production and HA; required for cluster mode (H:cluster; doc-only, no runtime guard found).
- Cassandra is a commercial Cyoda backend (`SRC/README.md:23`).

Postgres settings:
- `CYODA_POSTGRES_URL[_FILE]`, `_MAX_CONNS` (25), `_MIN_CONNS` (5), `_AUTO_MIGRATE` (true).
- Ceilings: `_STATEMENT_TIMEOUT` and `_IDLE_IN_TX_TIMEOUT` (5 m each; the latter must exceed `responseTimeoutMs`), `_ACQUIRE_TIMEOUT` (10 s), `_SEARCH_STATEMENT_TIMEOUT` (30 m).

### Getting models and workflows into a deployed instance

- **There is no seed or bootstrap mechanism.**
  - The subcommands are only `init`, `health`, `migrate` and `help` (`SRC/cmd/cyoda/main.go:62-77`).
  - No env var points at a model or workflow directory.
  - No init Job.
- **REST is the only path** (with a JWT in deployed mode; model and workflow endpoints don't require ROLE_ADMIN, any tenant token works):
  1. `POST /api/oauth/token` with the bootstrap or M2M client.
  2. `POST /api/model/import/JSON/SAMPLE_DATA/{e}/{v}` for each sample file.
  3. `PUT /api/model/{e}/{v}/lock`.
  4. Optionally `POST …/changeLevel/{lvl}` and `PUT …/unique-keys` (unique keys must be set before the lock).
  5. `POST /api/model/{e}/{v}/workflow/import` with `{"importMode":"REPLACE","workflows":[…]}`.
- **Idempotency:**
  - Re-importing a LOCKED model gets `409`. Check `GET /api/model/` `currentState` first.
  - Workflow REPLACE is idempotent.
  - gRPC `entityModelManage` is an alternative.
- **The project's versioned sample, workflow and config files** (build Step 3b) **are the deploy inputs.** JSON_SCHEMA exports can't be imported.
- **Compute nodes connect to gRPC 9090.** Through Helm this needs the GRPCRoute hostname or the gRPC ingress, with TLS at the edge. Use `CYODA_COMPUTE_GRPC_ENDPOINT` / `CYODA_COMPUTE_TOKEN`.

### Hardening checklist (H:quickstart PRODUCTION CHECKLIST)

- Postgres with `sslmode=require`.
- `CYODA_IAM_MODE=jwt` **and** `CYODA_REQUIRE_JWT=true`.
- Credentials only through `_FILE` vars or Secrets.
- The same `CYODA_HMAC_SECRET` on every node.
- A metrics bearer.
- TLS at the gateway or ingress; the binary has no TLS settings.
- `CYODA_ERROR_RESPONSE_MODE=sanitized` (the default).
- Pin the image tag.
- Rotate the bootstrap signing key before 365 days (`CYODA_IAM_KEYPAIR_DEFAULT_VALIDITY_DAYS`).
- Runtime keypairs and in-memory M2M clients are lost on restart.
- A pod latched to 503 after a recovered panic must be deleted manually; liveness doesn't restart it.

| L4 | Computed aggregations via "point-in-time or statistical queries" | **Accurate, name the tools** | Point-in-time works on get, list, search (direct and async), `/changes`, `/transitions`, grouped stats and conditional delete; it is inclusive (H:crud POINT-IN-TIME). "Statistical" means `GET /api/entity/stats…` (counts, counts by state) and `POST /api/entity/stats/{e}/{v}/query` (group by state or `$.field`; sum/avg/min/max/stdev; condition; `pointInTime`; cap `CYODA_STATS_GROUP_MAX`=10000 → 422). Works on all OSS backends (0.8.4 retired the 501). **Trino SQL analytics is Cloud-only** (H:analytics L13). Counter entities do collide under SI+FCW (409 retryable). Postgres point-in-time stats aren't covered by the shipped state index |
| L5 | Link via entity-id | **Accurate (convention only)** | No referential integrity, no joins in search, delete of a referenced entity isn't blocked. Composite unique keys exist but don't link |
| L9 | Workflows as first-class | Accurate | Design principle |
| L10 | Automated transitions for STP | **Accurate** | Cascade after every write: first matching non-manual, non-disabled, non-scheduled transition in declaration order, repeated (`SRC/internal/domain/workflow/engine.go:877-969`). Runs inside the write's transaction. Add: a `null`-criterion automated transition must come last, and scheduled transitions are a third kind |
| L11 | Manual transitions for external triggers; "processors use manual transitions on other entities" | **Needs nuance** | Manual = explicit `PUT/PATCH /api/entity/JSON/{id}/{t}` or gRPC `EntityTransitionRequest`; a cascade follows. A processor triggering others is an ordinary API callback, and its atomicity depends on mode and tx-token. **SYNC/ASYNC_SAME_TX:** echo `cyodatxtoken` as `X-Tx-Token`/`tx-token` to join the parent transaction, otherwise it runs standalone. **ASYNC_NEW_TX:** savepoint; failures discarded. **COMMIT_BEFORE_DISPATCH:** independent unless `startNewTxOnDispatch=true`; must be idempotent. The depth-2 nested-join deadlock was fixed in 0.8.3 (#410). Don't write the anchor entity and also return mutations. The engine does **not** enforce `manual:true`: a client can fire an automated transition by name; only disabled and scheduled ones are rejected (`engine.go:745-765`). "Manual-only" is a convention |
| L12 | Balance states | Accurate | Hard limits: 10 visits per state per cascade (`CYODA_MAX_STATE_VISITS`), depth 100 |
| L13 | "Execute a loopback transition to re-trigger automated transitions" | **Needs nuance / terminology** | In cyoda-go, loopback is **not a defined transition**. It is an update without a transition name (`PUT /api/entity/JSON/{id}` or `PATCH …/{id}`), which re-runs the automated cascade from the current state (`engine.go:493-579`; `meta.transitionForLatestSave="loopback"`). To re-evaluate without changing data: `PATCH` with `{}` (merge-patch, `If-Match`); "the empty patch still commits a new transaction and fires the loopback" (H:crud). An explicit self-transition (`next` = same state) is also legal when manual; unguarded automated self-loops are rejected at import unless `allowCycles:true`. A runaway cascade aborts and rolls back the write. Loopback/settled writes **re-arm scheduled timers** (postponing them) |
| L14 | Validation cycles | Accurate | Back-edges are fine; automated back-edges need a criterion or `allowCycles` (`validate.go:635-647`) |
| L15 | Errored state; "Monitors can query…"; "Notifications (coming soon)" | **Stale** | No notification, webhook or subscription feature exists in code, help, CHANGELOG, proto or docs. It is not on the Cloud roadmap either (`cyoda-docs/.../cyoda-cloud/status-and-roadmap.md`). "Monitors" = polling `GET /api/entity/stats/states/{e}/{v}?states=Errored` or a search. Today's options: an `ASYNC_NEW_TX` processor on the transition into the error state (the documented use for "notifications, audit pings", `docs/PROCESSOR_EXECUTION_MODES.md:45`), or a scheduled transition for escalation |
| L16 | Backward transitions for retries | Accurate | Docs payment example uses amend/retry |
| L17 | "Always supply a rejection reason in criteria" | **Needs nuance** | Only **`function` criteria** (compute node) can supply one: `EntityCriteriaCalculationResponse.reason` on `matches:false`, v0.8.3+, ≤2 KiB. Inline simple/lifecycle/group/array criteria always record the default "criterion did not match". Surfaces: manual rejection → `400 WORKFLOW_FAILED` detail `transition "<n>" criterion not matched: <reason>` (the audit event is **not** durable; that transaction rolls back); automated cascade → durable `TRANSITION_NOT_MATCH_CRITERION.data.reason`; workflow selection → `WORKFLOW_SKIP.data.reason` (H:grpc; CHANGELOG #413). Inline criteria can use `criterionAnnotations.description` for human-readable intent |
| L18 | Ledger over deletion | **Accurate; add facts** | Delete exists: `DELETE /api/entity/{id}` and `DELETE /api/entity/{e}/{v}`. On the latter an **empty body deletes all**; with a condition it deletes the matching subset (`transactionSize`, `pointInTime`, `verbose`). Delete is **soft**: a tombstone is added, history kept, a point-in-time read before the delete still works, `/changes` shows `DELETE`. **Delete bypasses the workflow** (no transition, processor or criterion), which is a strong reason to prefer terminal states. It frees unique-key values |
| L19 | Precise terminal states | Accurate | No engine "terminal" flag; a state with no automated transitions is stable. Multiple terminals are a modelling choice |

## 5. Cloud coupling in cyoda-go the dev skills should avoid

- **`cyoda help analytics`** (Trino SQL, `/api/sql/schema/*`, STOMP `treeNode.*`/`reports.*`): marked **Cloud-only**, not in the binary (H:analytics L13). Don't route "SQL/reporting" questions there.
- **OpenAPI stubs for Cloud-only surfaces:**
  - `/api/platform-api/stream-data/*`, `/api/account/subscriptions` (501, `SRC/internal/api/unimplemented.go`).
  - `getTechnicalUserToken` naming.
  - `/api/platform-api/entity/fetch/transitions` (legacy `Name.Version` format; use `/api/entity/{id}/transitions`).
- **Accepted-but-not-implemented parity fields:**
  - `asyncResult:true` / `crossoverToAsyncMs` are rejected at import.
  - `retryPolicy` is accepted but ignored (single-shot).
  - Processor `type:"internalized"` is reserved and fails at dispatch.
  - `IDEMPOTENCY_CONFLICT` is reserved.
  - `waitForConsistencyAfter` is ignored.
  - Don't generate workflows that rely on any of these.
- **Commercial-backend items:**
  - Audit `eventType=System` is never emitted by OSS.
  - `COMPOSITE_KEY_UNSUPPORTED` comes from the commercial backend.
  - Cassandra.
  - Shard-routing / `TRANSACTION_EXEC` audit details (the debug skill L97 assumes them).
- **Cloud-shaped JWT claims** (`caas_org_id`, `caas_user_id`, `caas_tier` = "unlimited") and names (`org.cyoda.cloud.api.grpc`, `cyoda-cloud-api.proto`, `$id https://cyoda.com/cloud/event/...`): naming only. Safe to use; they are the real contract.
- **`docs/cloud-parity/*` and "Cloud parity" notes in help:** contracts that describe where OSS intentionally matches or diverges from Cloud. Good reference, but the dev skills should cite the OSS behavior only.
- **In the skills themselves:** Cloud hostnames (`client-…-dev.eu.cyoda.net`, the `grpc-` prefix), the "post-redeploy technical users deleted" note, "contact the Cyoda team", the `env: production` → "Cyoda Cloud [PRODUCTION]" label, and the whole `migrate` skill.
  - The production guard is still useful for self-hosted prod. Key it off the profile's `env`, not "cloud".
